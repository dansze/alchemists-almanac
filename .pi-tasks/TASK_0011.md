CONTEXT
- The `.omwscripts` manifest declares three contexts: `GLOBAL` (init.lua), `LOAD` (load-db.lua), and `PLAYER` (alchemy-binding.lua); each context runs in a separate sandbox, and `onSave()`/`onLoad()` handlers are invoked per-script during save/load cycles.
- LOAD-context scripts do **not** re-execute after `reloadlua` (0.51.0+ hard limit); only a full game restart reloads them, meaning the PLAYER context's `onLoad()` must handle the case where the effect database was not rebuilt.
- The `onObjectAdded(object)` engine handler is documented as a **local-context** handler receiving a single `object` parameter; the API reference confirms this signature but provides no further detail on whether the payload distinguishes inventory additions vs. world spawns, nor whether the object reference includes parent/entity context.
- `onSave()` must return a plain Lua table (only serializable types: nil, numbers, strings, tables with serializable keys/values); functions, custom metatables, shared references, and circular references are explicitly **not serializable**.
- Persisted data sizes have **no documented limits** in OpenMW 0.50+ (payload size, nesting depth, key count are all marked unverified); the discovered recipes table could grow to O(N²) for 2-ingredient pairs and O(N³) for 3-ingredient combos across all ingredients, requiring a conservative schema design.
- `interfaces.AlchemyHelper.queryEffects(ids)` is a live runtime closure over the LOAD-built effect database; interface methods are **not persisted** — they are resolved at runtime via `require('openmw.interfaces')` and exist only in memory.
- The LOAD-context `load-db.lua` already registers `AlchemyHelper` with a `queryEffects` method returning `{ingredients, sharedIngredient, pairs, triples, recipes}` per effect ID; the return value is a plain table and does not touch serialization.
- Ingredient IDs are stored as strings in all lookup tables (`pairEffects["id1:id2"]`, `tripleEffects["id1:id2:id3"]`), and effect IDs are also strings (`effId`); the API reference notes "store effect IDs as integers" for serialization, but the actual codebase uses string IDs — this is a design tension for the save schema.
- The `onObjectAdded()` handler will fire for **all** object additions (not just player inventory), so the PLAYER-context script must distinguish player inventory additions from world/container additions — the `object` parameter's structure (does it have a `parent` or `refId` to check ownership?) is unverified and must be treated as a known-unknown.
- Potion effects in OpenMW are accessible via `types.PotionRecord.effects` (full `MagicEffectWithParams`), but `onObjectAdded()` does **not** directly provide effect data — the added object's record must be resolved via `types.Potion.record(objectId)` (PLAYER context) to read the `effects` field, which contains the magic effect IDs needed for reverse-lookup.
- The existing `load-db.lua` already builds `pairEffects` (2-ing key → effect IDs) and `tripleEffects` (3-ing key → effect IDs) with canonical sorted-string keys; discovered recipes should be stored as plain arrays of these canonical keys (strings), not as ingredient ID objects, to remain serializable.
- The `load-db.lua` module table exports `interfaceName = 'AlchemyHelper'` and `interface = { queryEffects = ... }` alongside `engineHandlers` — this is the established pattern; the new persistence handlers (`onSave`/`onLoad`) should be added to the PLAYER context (alchemy-binding.lua) since player progress is player-scoped.
- The `openmw.storage` package (`require('openmw.storage')`) exists as an alternative persistence API with `storage.set(key, value)` / `storage.get(key)`, but its availability, key namespace scoping (per-mod? per-script?), and serialization compatibility with `onSave()`/`onLoad()` are **not verified** in OpenMW 0.50+ documentation and should be treated as a known-unknown.
- UI preferences are not yet implemented (Steps 6–8 deferred); the persistence schema should reserve a `preferences` key that can later hold panel position, theme, and visibility state, but the current implementation should only define the placeholder structure.
- Recipe discovery storage strategy: store as `{ version = 1, discovered = { "id1:id2", "id1:id2:id3", ... }, preferences = {} }` — a flat array of canonical ingredient key strings (not nested tables) minimizes serialization complexity and avoids multi-reference/circular-reference issues.
