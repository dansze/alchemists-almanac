CONTEXT
- The `.omwscripts` manifest uses a plain-text `<flags>: <path>` line format (not INI, not XML, not JSON); lines prefixed with `#` are comments, and the manifest file sits at the mod's data-directory root level (e.g., `alchemy-helper.omwscripts` at the same level as `scripts/`).
- The `LOAD` flag in `.omwscripts` is new in OpenMW 0.51.0 and is explicitly excluded from 0.50+; since the task targets 0.50+, only `GLOBAL`, `MENU`, `PLAYER`, `CUSTOM`, and the auto-attach flags (`ACTIVATOR`, `NPC`, `INGREDIENT`, etc.) are available.
- The `LOAD` context does not re-run after `reloadlua` in 0.51.0+ — a full game restart is required, which is a runtime constraint the documentation must communicate.
- The `scripts/omw/` directory is reserved for built-in OpenMW scripts and must not be used by the mod.
- The recommended directory layout places scripts under `scripts/<ModName>/<ScriptName>.lua` — per the API reference Section 1.4 — so `scripts/alchemy-helper/main.lua` is the canonical entry-point location, with `scripts/alchemy-helper/player.lua` and other context-specific scripts following the same convention.
- The mod directory name is `alchemy-helper` while the spec names the mod "Alchemist's Almanac"; the task explicitly says to keep the directory name and clarify the relationship in documentation rather than rename anything.
- OpenMW's `openmw.cfg` can register a mod either as `data=path/to/mod_dir` (mounting the entire directory into the VFS) or as `content=my_mod.omwscripts` (pointing to the manifest directly); both are valid for 0.50+.
- No `.omwaddon` manifest format is implemented in OpenMW 0.50+; the `openmw.addon` / `.omwaddon` feature is noted as "not implemented yet" and must be avoided.
- A valid OpenMW Lua script returns a table with optional keys: `engineHandlers`, `eventHandlers`, `interfaceName`, and `interface`; the minimal viable script is `{ engineHandlers = { onUpdate = function() end } }`.
- The `openmw.cfg` registration snippet in documentation should include both a comment explaining the mod's purpose and the exact directive(s) needed, plus a note about where to place the mod directory relative to OpenMW's data search path.
- The `Settings` interface (available in global/menu/player contexts) is the documented mechanism for persistent configuration; the spec's "Immersive Mode" toggle can be wired through this interface, but the exact API contract for `Settings` is not detailed in the reference.
- The player script context has access to `openmw.input` and the `onKeyPress(key)` engine handler, which is the mechanism for implementing the "configurable key" to open the UI; however, the API reference does not document a built-in keybinding registry — the mod must implement its own input polling.
- `onObjectAdded(object)` is an engine handler available in local/player contexts for tracking ingredients entering the player's inventory; the handler receives an object reference, not a record ID, requiring `require('openmw.self')` or type checks to identify the ingredient.
- `world.activeActors` is available in the global context and provides the list of actors in currently loaded cells — this is the handle for cell-change merchant detection, not a dedicated "cell-changed" event handler.
- Serialization constraints for `onSave()`/`onLoad()`: only `nil`, numbers, strings, game objects, `util.vector3`, and plain tables (no functions, no custom metatables, no circular references) are serializable; any saved data structure must comply.
- The TODO's reference to `scripts/alchemy-helper/init.lua` as a stub is consistent with the `<ModName>/<ScriptName>.lua` layout; the file name `init.lua` is a convention but OpenMW does not mandate a specific script filename beyond what's referenced in the manifest.
- Multiple flags in `.omwscripts` can be combined on a single line using space or comma as a separator, enabling a single Lua file to serve as both a player script and a menu script if needed.
- The mod's `data/` directory is left empty in Step 1 but should be present in the scaffold for future assets (UI textures, custom models, data files); it is a no-op now but provides forward compatibility.
- OpenMW's sandbox prohibits loading DLLs and precompiled Lua files (`.luac`); all mod code must be plain `.lua` text files not packed into archives for `reloadlua` support.
