CONTEXT
- `init.lua` is a GLOBAL script (per `.omwscripts`), meaning its `onSave`/`onLoad` handlers persist across game sessions via the OpenMW engine; the return table's `engineHandlers` field is what registers these with the engine.
- `load-db.lua` is a LOAD script, meaning it rebuilds `pairEffects`, `tripleEffects`, and `recipeEffects` from scratch every time the game loads — these are the live tables used by `queryEffects`.
- `init.lua`'s `pairEffects`, `tripleEffects`, and `recipeEffects` are dead: nothing calls `require('scripts.alchemy-helper.init')` for those keys — the only consumer of the return table is `alchemy-ui.lua`, which reads only `ingredientEffects`.
- The `ingredientIds` array (lines ~101–104) is exclusively consumed by the `pairEffects` build (lines ~109–136) and `tripleEffects` build (lines ~142–201); removing it does not affect `ingredientEffects`, `effectIngredients`, `sharedIngredients`, or `effectNames`.
- The `sharedIngredients` build (lines ~224–260) depends only on `effectIngredients` and `ingredientEffects`, not on `pairEffects`/`tripleEffects`, so it is unaffected by the deletion.
- `alchemy-ui.lua` line 13 does `local ingredientEffects = lookupTables.ingredientEffects or {}` — it never accesses `pairEffects`, `tripleEffects`, `recipeEffects`, or `sharedIngredients` from the `init.lua` return table.
- `load-db.lua` registers `AlchemyHelper` interface with `queryEffects` and delegates `discoverIngredient` to `init.lua`, confirming the separation: `init.lua` owns persistence, `load-db.lua` owns the live effect database.
- The v1 migration in `onLoad` handles a legacy schema where `saved.discovered` entries were colon-separated ingredient keys (e.g., `"ingId1:ingId2"`); after migration it splits on `:` and inserts each part individually into `discoveredMap`.
- If `version = 2` is removed from the `onSave` return and the v1 branch from `onLoad`, any previously saved data with `version = 1` will silently fail the `version` check and be rejected — this is only a concern if players have legacy saves.
- The `.omwscripts` manifest uses `GLOBAL:` and `LOAD:` directives for script lifecycle contexts; it does not reference engine handlers or version numbers, so no manifest change is needed for table removals.
- The `recipeEffects` build is purely a union of `pairEffects` and `tripleEffects` (copy-by-reference of values), so it is dead even within `init.lua` itself — no internal code references `recipeEffects`.
- `onSave` currently returns `{ version = 2, discovered = ..., preferences = ... }`; removing `version = 2` means `onLoad` receives `{ discovered = ..., preferences = ... }` with no `version` key, so the simplified `onLoad` should just check for truthy `saved` and merge directly.
- The `version` field in `onLoad` is used as a discriminator between v1 (migration path) and v2 (direct restore); after removing v1, the `if version == 1` branch and the `elseif version == 2` branch both collapse into a single path, making the `version` field meaningless.
- `ingredientEffects` in `init.lua` is built from `types.Ingredient.records` (which includes all ingredients from all loaded ESPs/ESMs), while `load-db.lua` builds its own copies using `content` API — the two may diverge if mods add/remove ingredients between global-load time and load-context time, making `init.lua`'s tables redundant.
