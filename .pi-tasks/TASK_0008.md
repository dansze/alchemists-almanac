- The effect database is built in LOAD-context by `scripts/alchemy-helper/load-db.lua` and exposed via `interfaces.AlchemyHelper.queryEffects(ids)`, which returns for each effect ID a table `{ ingredients = {ingId...}, sharedIngredient = ingId?, pairs = {"a:b"...}, triples = {"a:b:c"...}, recipes = {"a:b"...} }`.
- `load-db.lua` uses `content.ingredients.records` (LOAD context, available from 0.51.0+); `init.lua` (GLOBAL context) uses `types.Ingredient.records` as a fallback for earlier versions.
- The exact API surface of `openmw.ui` (primitives, properties, methods) and `openmw_aux.ui` (utility functions) is not documented in the project's own docs — the API reference only lists `openmw.ui` as "Controls the user interface" and `openmw_aux.ui` as "User interface utilities" available in menu/player contexts — so signatures for `ui.create()`, `ui.TYPE.*`, `ui.content()`, and any `openmw_aux.ui.*` helpers must be inferred from the EXTERNAL CONTEXT or left as open questions.
- The `.omwscripts` manifest (`alchemy-helper.omwscripts`) currently registers only two scripts: a `GLOBAL:` entry for `init.lua` and a `LOAD:` entry for `load-db.lua`; a new UI module would need its own PLAYER or MENU context line added to the manifest.
- `onKeyPress(key)` is available only in PLAYER and MENU contexts (not GLOBAL/LOCAL/LOAD), so any toggle mechanism must be a PLAYER or MENU context script.
- The constraint forbids `pcall`-wrapping infrastructure, meaning the UI module must not include its own error-guard layer — it should fail loudly if misused rather than defensively wrapping.
- The constraint also forbids keybind wiring and auto-detection of the alchemy menu — the panel creation function must be independently callable without relying on step-7's menu detection or step-9's persistence.
- `openmw_aux.ui` is available in both menu and player contexts (per the API reference table), so the UI module can live in either context depending on whether it's intended as a standalone overlay or integrated into an existing menu flow.
- The panel data contract: `queryEffects(ids)` takes an array of effect ID strings and returns a table keyed by effect ID, each value containing `ingredients` (array of ingredient IDs), `sharedIngredient` (single ingredient ID or nil), `pairs` (array of colon-separated ingredient pair keys), `triples` (array of colon-separated triple keys), and `recipes` (union of pair and triple keys).
- Serialization constraints (from SANDBOX_CONSTRAINTS.md §8) prohibit storing functions, custom metatables, shared references, or circular references in `onSave()` data; however, since the UI panel is a transient runtime object not involved in save/load, these constraints apply to any config or persistent state the module might store separately.
- `reloadlua` does not re-execute LOAD-context scripts, so after hot-reload the `interfaces.AlchemyHelper` interface may be `nil` if the game is still in a PLAYER session — the UI module should tolerate a missing interface or document this as a required restart condition.
- The module naming convention follows the project pattern: scripts live under `scripts/alchemy-helper/` and the module path is determined by the `.omwscripts` manifest registration (e.g., `scripts/alchemy-helper/alchemy-ui.lua` would be referenced as `scripts/alchemy-helper/alchemy-ui.lua` in the manifest).
- OpenMW's UI system uses layout tables with `type`, `props`, and `events` fields (per OpenMW docs), where `type` comes from `openmw.ui.TYPE` — this is the mechanism by which windows, panels, labels, lists, and buttons are instantiated.
