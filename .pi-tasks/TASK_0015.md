CONTEXT
- `discoveredMap` in `init.lua` (line 294) is a plain Lua table keyed by canonical recipe combination strings like `"ing1:id:ing2:id"` — this entire data structure must be replaced with individual ingredient ID keys
- `discoverRecipe(ingredientIds)` (init.lua line 332) deduplicates and sorts 2-3 ingredient IDs into a sorted colon-separated key, then checks if that key exists in `pairEffects` or `tripleEffects` — this recipe-resolution logic must be removed entirely
- `onSave()` (init.lua line 361) serializes `discoveredMap` as `{ version = 1, discovered = { "key1", "key2", ... }, preferences = preferences }` — the `version` field should stay `1` (or be bumped to `2` for migration), and `discovered` values change from recipe combination keys to individual ingredient IDs
- `onLoad()` (init.lua line 377) restores `discoveredMap` from saved keys AND iterates player inventory potions to re-discover recipes — this must instead re-discover ingredients from existing inventory
- `onObjectAdded(object)` (init.lua line 423) is declared in `init.lua` which is a **GLOBAL context** script, but `onObjectAdded` is documented as **LOCAL-only** in SANDBOX_CONSTRAINTS.md (§9 table) — this may be a current implementation bug; ingredient pickup detection may need to run in a LOCAL context script
- The current `onObjectAdded` handler detects **potions** in player inventory (via `getInventory()` scan then `getPotionIngredients()`), then resolves ingredients from potion records — ingredient tracking needs to detect **ingredient-type objects** directly instead
- `getPotionIngredients()` (init.lua line 312) uses `content.potions.record(potionId)` and `types.Potion.record(potionId)` to extract `effects[].ingredient` — this function is only needed for the current recipe discovery and should be removed
- `load-db.lua` runs in **LOAD context** and builds the static effect database; it has no persistence/discovery logic — no changes needed to `load-db.lua`
- `alchemy-ui.lua` displays effects for a given ID via `queryEffects()` — it does not reference discovered recipes at all, so no UI changes are needed for the tracking subject change
- `alchemy-binding.lua` is a PLAYER context script that triggers the UI — it has no dependency on the discovery mechanism
- The omwscripts manifest (`alchemy-helper.omwscripts`) declares `init.lua` as `GLOBAL`, `load-db.lua` as `LOAD`, and `alchemy-binding.lua` as `PLAYER` — adding ingredient pickup detection may require a new LOCAL context script entry
- OpenMW sandbox serialization (SANDBOX_CONSTRAINTS §8) only supports nil, numbers, strings, plain tables with serializable keys/values, and game objects — ingredient ID strings fully comply
- `reloadlua` does **not** re-execute LOAD-context scripts (`load-db.lua`), but `init.lua` (GLOBAL) **is** reloaded via `reloadlua` — this is relevant for iterating on changes to ingredient detection
- The `preferences` table in the save schema is currently empty and should be preserved as-is in the new ingredient-based save format
