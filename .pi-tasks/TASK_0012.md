## refined prompt

GOAL
  All record lookups (ingredient, effect, ESP data) and database queries are wrapped in `pcall` to prevent unhandled errors from crashing the script. Missing ingredients, unloaded ESPs, duplicate ingredient selections in the alchemy menu, and uninitialized database states (e.g., PLAYER context before LOAD completes) are handled gracefully with sensible defaults or early returns. Startup table builds are batched or structured to avoid single-cycle pauses exceeding 1 second, ensuring the script degrades gracefully rather than freezing the game.

CONSTRAINTS
  - Do not change the existing database schema, effect lookup tables, or recipe reverse lookup logic built in steps 3–5.
  - Preserve all existing interface wiring: `interfaces.AlchemyHelper.queryEffects(ids)`, `onSave()`, `onLoad()`, `onActivated()`, `onObjectAdded()`.
  - Do not alter the persisted save schema (discovered recipes and preferences) defined in step 9.
  - Do not modify the UI panel structure from step 6 or the keybind detection from step 7.
  - Do not introduce custom metatables in config code (step 8 decision).
  - All `pcall` wrappers must log or suppress errors silently without masking logic bugs; avoid swallowing errors that indicate real failures.
  - Batch startup builds must not reorder or skip any required lookup table entries.
  - Graceful degradation means the script continues functioning at a reduced capacity (e.g., no lookups available) rather than crashing.
  - Preserve Lua 5.1 sandbox compliance and serialization limits for `onSave()`/`onLoad()`.

KNOWN-UNKNOWNS
  - What is the exact magnitude of the startup table builds? How many entries must be constructed, and are they already incremental or all done in one pass?
  - Is there an existing error logging mechanism in the script, or should `pcall` error paths simply silently return nil/empty tables?
  - How are duplicate ingredient selections currently represented in the alchemy menu context (e.g., array of IDs, and are there already duplicates at that level)?
  - What constitutes "uninitialized database" from a PLAYER context — is there a version flag or a boolean guard currently in place?
  - Are there known ESPs that players commonly unload that contain alchemy-related records we should proactively handle?
  - Is `interfaces.AlchemyHelper.queryEffects` already defined, or does its implementation need the defensive wrappers as part of this step?

CONTEXT
- `init.lua` runs in GLOBAL context and builds lookup tables from `types.Ingredient.records`; `load-db.lua` runs in LOAD context and builds the same tables from `content.ingredients.records` — both files contain nearly identical table-building logic, meaning there is a duplication risk if schema or logic changes.
- `load-db.lua` registers `interfaces.AlchemyHelper` with a `queryEffects(ids)` method that is a live closure over the in-memory tables built during LOAD — this data is NOT serialized into saves, so the interface is fully rebuilt from scratch on every LOAD.
- No existing `pcall` wrappers exist anywhere in the script codebase (confirmed via grep): `init.lua`, `load-db.lua`, and `alchemy-binding.lua` all lack error guards.
- The `reloadlua` limitation is documented and partially addressed in `alchemy-binding.lua` (it nil-checks `interfaces.AlchemyHelper.queryEffects`), but the `load-db.lua` and `init.lua` files have no such guards — any PLAYER/MENU caller that accesses these tables before LOAD completes or after reloadlua will crash.
- `content.ingredients.records` (LOAD context) only populates `effects[].id`, `effects[].affectedAttribute`, and `effects[].affectedSkill` — it does NOT populate `effects[].range`, `effects[].area`, `effects[].duration`, `effects[].magnMin`, `effects[].magnMax` — the magnitude multiplier calculations in `load-db.lua` use hardcoded `fPotionStrengthMult = 1.0` since `core.getGMST` is not available in LOAD without `openmw.core`.
- `init.lua` (GLOBAL context) uses `core.getGMST('fPotionStrengthMult')` and `core.getGMST('fPotionT1MagMul')` for actual magnitude values — this means magnitude calculations differ between the GLOBAL and LOAD code paths.
- The pair/triple effect intersection logic is O(n_ingredients²) and O(n_ingredients³) respectively — with n_ingredients likely in the thousands for a full Morrowind mod, this could easily exceed the 1-second startup threshold in a single GC cycle.
- `interfaces.AlchemyHelper.ingredientId()` is called in `alchemy-binding.lua` but is NOT defined in `load-db.lua` — the interface table only contains `queryEffects`; the `ingredientId()` method must be added by an external UI module or is missing.
- The save schema uses `version = 1` with migration stubs for versions 2 and 3, but only version 1 produces data — unknown versions are rejected silently with no logging.
- `discoveredMap` is stored as `{ key = true }` (set semantics) in `init.lua` but loaded from a flat array `{ keys... }` in the save schema — the `onSave()` serializes keys to an array and `onLoad()` reconstructs the set.
- `alchemy-binding.lua` references `require('alchemy-ui')` which is not in the project file inventory, indicating the UI module is either external or not yet committed — any dependency chain should account for missing requires gracefully.
- `load-db.lua` has a comment suggesting incremental caching with a generation counter if table builds exceed 1s, but no such mechanism is implemented — the build is currently monolithic.
- The `onObjectAdded()` handler in `init.lua` iterates `getInventory()` to check object ownership, which is O(n_inventory) per call — this could be slow with large inventories.
- `onLoad()` in `init.lua` calls `openmw.player.getInventory()` during load — if `openmw.player` is nil or `getInventory()` is unavailable, the function silently skips inventory re-discovery without logging.
