CONTEXT
- The existing `scripts/alchemy-helper/init.lua` is a GLOBAL-context script (declared via `GLOBAL:` in `alchemy-helper.omwscripts`) that already builds lookup tables: `ingredientEffects`, `effectIngredients`, `pairEffects`, `tripleEffects`, `recipeEffects`, `sharedIngredients`, and `effectNames` — all constructed at module-load time from `types.Ingredient.records` and `content.magicEffects.records`.
- The task requires a **LOAD-context** script (0.51.0+ only), meaning a separate manifest entry `LOAD: scripts/alchemy-helper/...` must be added, and the script file must be a distinct module or the existing script must detect context — OpenMW LOAD scripts are loaded separately from GLOBAL scripts.
- LOAD context scripts **do NOT re-run after `reloadlua`** (confirmed in `SANDBOX_CONSTRAINTS.md` §7 and `phase-3-investigation.md` §8.3); only a full game restart re-execs them — this is the core reason PLAYER-context callers must guard against an uninitialized database.
- During LOAD context, only `openmw.content` and `openmw.types` are usable; `openmw.world.*` functions are **unavailable** because the game world is not yet initialized (`phase-3-investigation.md` §7.2).
- In LOAD context, `content.ingredients.records[].effects` entries are **truncated** to only three fields (`id`, `affectedAttribute`, `affectedSkill`); all other `MagicEffectWithParams` fields (`range`, `area`, `duration`, `magnMin`, `magnMax`, `index`) are **not populated** — but the C++ engine hard-codes these to `RT_Self`, `0`, `0`, `0`, `0`, `0` anyway, so the truncated data is sufficient for effect-ID matching.
- `content.ingredients.records` is **mutable** in LOAD context but **unavailable** in PLAYER context; `types.Ingredient.records` is read-only in both contexts — the database build must iterate `content.ingredients.records` in LOAD or `types.Ingredient.records` otherwise.
- Script interfaces in OpenMW are registered via the script's return table using the `interfaceName` and `interface` keys (`openmw-lua-api-reference.md` §2.8); consumers access them via `require('openmw.interfaces')` then `interfaces.AlchemyHelper.queryEffects(ids)` — the `interface` value must be a plain table of callable functions (no metatables, no closures with non-serializable captures).
- Interface data is resolved at runtime via `openmw.interfaces` and is **not persisted into game saves** (`SANDBOX_CONSTRAINTS.md` §8.5).
- The `onContentFilesLoaded()` handler (0.51.0+, LOAD-only) fires after all content files are parsed but before the main menu appears — it is the **earliest reliable point** where `content.ingredients.records` is fully populated for database construction (`phase-3-investigation.md` §8.3).
- LOAD context scripts support `onInit()` and `onContentFilesLoaded()`; `onInit()` fires before `onContentFilesLoaded()`, so building the database in `onInit()` risks accessing records that are not fully populated.
- Lua 5.1 sandbox rules apply: no `dofile`, no `loadlib`, no `loadstring`, no `debug` library, no `io` module; only `os.date`, `os.time`, `os.difftime` from `os` are allowed (`SANDBOX_CONSTRAINTS.md` §6).
- Functions cannot be serialized (`SANDBOX_CONSTRAINTS.md` §8.2) — the `queryEffects` function is a **live runtime call**, not persisted data, which is why the interface approach works.
- The `queryEffects(ids)` return shape must map each effect ID in the input list to its data: `effectIngredients[effId]` (list of ingredient IDs providing that effect) and any multi-ingredient recipe matches from `pairEffects` / `tripleEffects` — the exact return structure should mirror the lookup tables already built in `init.lua`.
- The `ids` argument is described as "a list of effect IDs" — this is a Lua table/array of effect ID strings (e.g., `{"FireDamage", "Vampirism"}`), and the function should return a table keyed by each effect ID with its corresponding ingredient and recipe data.
- OpenMW 0.50 does **not** have the LOAD context or `onContentFilesLoaded()` (those are 0.51.0+); a 0.50-compatible fallback would need to use `onInit()` in a GLOBAL context script, but the task explicitly targets 0.50+.
- The `require()` mechanism loads each script file once and caches it; multiple `require('same_module')` calls return the same cached return value — the database must be built into module-level upvalues so the interface function closes over them.
