GOAL
  Create a Lua script that runs in the OpenMW LOAD context to build a complete alchemy effect database at game content-load time. The script must register the built database as a callable function on `interfaces.AlchemyHelper.queryEffects(ids)` so that other scripts (from later steps) can query it by passing a list of ingredient/ingredient-pair effect IDs. The database is fully rebuilt from scratch on each LOAD event (nothing from a previous session is reused for the effect tables). Additionally, document the `reloadlua` console command limitation: if the user triggers `reloadlua` while a PLAYER context is active (e.g., during gameplay), the effect database may be uninitialized at that point; the documentation must explain this gap and describe how PLAYER-context callers should guard against it (e.g., checking for `nil` before querying, or deferring queries until LOAD has fired).

  - Do NOT touch step [1] (`.omwscripts` manifest, directory structure, mod registration docs), step [2] (sandbox constraints doc), step [3] (ingredient/ingredient-record field investigation), or step [4] (lookup tables) — these are already [done].
  - Preserve the exact interface signature: `interfaces.AlchemyHelper.queryEffects(ids)` — this is a pinned fact from the cross-slice contract; consumers will call this exact name with a list of effect IDs and expect effect lookup results.
  - The effect database must be fully rebuilt at LOAD time (decision confirmed in step 5); do NOT attempt incremental updates or partial caching of the effect lookup tables.
  - Only player discoveries (discovered recipes) and preferences are persisted via `onSave()`/`onLoad()` hooks — these are owned by step [9]; do NOT implement persistence in this step.
  - The script must target OpenMW 0.50+ and respect Lua 5.1 sandbox constraints documented in step [2] (no `dofile`, no `loadlib`, no `os.execute`, etc.).
  - Do NOT invent OpenMW API surface area — only use documented hooks/events (`LOAD`, `interfaces` registration) known from steps [2] and [3] investigation.

  - The `queryEffects` function must accept a list/array of effect IDs and return the corresponding effect data (ingredient list, effects, or potion recipes) — follow the exact return shape implied by the step [4] lookup tables (ingredient → effects, effects → shared ingredients, pair/triple → potion effects).
